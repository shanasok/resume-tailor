# Resume Handler — Project Brief

## Vision
Automate resume tailoring and job applications in three phases:

- **Phase 1** ✅ _Complete_ — Take a base resume + job posting → generate a perfectly tailored resume optimized for ATS
- **Phase 2** — Source matching jobs from LinkedIn automatically, then run Phase 1 for each
- **Phase 3** — Automatically apply to each job using the tailored resume

## Current Status
**Phase 1 complete. Phase 2 discovery + AI ranking built (wide-net sieve, pgvector Match %, ChatGPT fit verdicts); auto-generation per match is the remaining Phase 2 piece.**

Phase 1 is fully built and tested, with both a CLI and a web UI.

**Web UI (recommended):**
```bash
docker compose up --build      # app + Postgres → http://127.0.0.1:5001
# — or run the app locally against the docker DB —
docker compose up -d db
source .venv/bin/activate
python app.py     # then open http://127.0.0.1:5001 (5000 is taken by macOS AirPlay)
```
Form takes company, role, and a job URL or pasted text; shows application history with preview/download links.
Tests: `.venv/bin/python -m pytest tests/ -v` (447 tests; the DB-backed ones skip unless the docker db is up — they use a throwaway `resume_handler_test` database, never the real one; the pgvector tests additionally skip if the db image lacks the `vector` extension)

**CLI:**
```bash
python main.py --company "Acme Corp" --role "Director of Engineering" --job-file path/to/posting.txt
# or --job-url https://... or --job-text "paste text here"
```
Outputs: `resumes/generated_resumes/<company>_<role>_resume.html` + `.pdf`

## Architecture
- `src/pipeline.py` — `generate(user_id, company, role, source, max_pages=2, min_pages=2, max_attempts=2, max_polish=2, min_score=85, use_external_critic=True, use_evidence=True, allow_resume=False, on_progress=None)`: the shared Phase 1 pipeline used by BOTH `main.py` (CLI) and `app.py` (web). Edit pipeline logic here once. Returns `(html_path, pdf_path, meta)` where `meta = {pages, attempts, fit, too_short, resumed, evidence_used, …}`.
  - **Evidence pre-pass (`src/evidence.py` `extract_evidence`; `use_evidence`, default on; CLI `--no-evidence`):** BEFORE any tailoring, one LLM call (on the generate-stage backend) reads the posting + base résumé and returns a GROUNDING MAP — each posting requirement → the candidate's real matching evidence + confidence + source role, plus a ranked must/should/optional list, with genuine gaps named as honest gaps (confidence "None"). `format_evidence` renders it into `tailor_resume(..., evidence=)`'s cached prefix, so BOTH passes WRITE from the map instead of re-retrieving while composing — the strongest true matches reliably surface near the top and the model stops papering over gaps. Adds NO facts (everything still traces to the base résumé). Fully optional: any failure degrades to tailoring without it.
  - **Tailoring prompt constraints (`tailoring._INSTRUCTIONS`/`_SCHEMA`):** prefer SELECTION over rewriting (reorder/re-emphasize; rewrite a bullet only for relevance/redundancy/clarity, minimal words); competencies must be concrete real skills/tools/domains, not abstract business phrases; use the industry-standard NAME for a skill the candidate genuinely has (ATS) without renaming a real thing into a bigger one; the SUMMARY (the most drift-prone section) must be 3-4 SEPARATE short sentences, must NOT merge two base facts into one causal claim, and must keep the base résumé's own scope wording. The polish editor (`_POLISH_INSTRUCTIONS`) enforces the SAME summary rules as a surgical fix.
  - **Resumable generation (checkpointing; `allow_resume`, `CKPT_MAX_AGE_SEC`):** each expensive stage (evidence map, Pass-1 draft, external review, latest Pass-2/polish draft) is written to a per-résumé `.checkpoints/<slug>/` folder (under the résumé's out_dir) AS SOON AS it finishes — the Pass-2 draft is saved right before the critic, the usual failure point. A run with `allow_resume=True` (the app passes it on every generate) REUSES a checkpoint set whose SIGNATURE matches (the four stage LLMs + a hash of the résumé & posting text) and is < 6h old, so a failed generation CONTINUES from where it stopped instead of re-paying every earlier Claude call; a signature/age mismatch starts fresh. Cleared on SUCCESS (a failure leaves them for the next retry). All writes best-effort — a checkpoint failure never breaks a generation. `meta["resumed"]` records whether a run continued one. No new UI button: re-clicking the same regenerate resumes, and the failure message says so.
  - **Quality + length feedback loop:** each attempt = tailor → render → count pages (`renderer.count_pdf_pages`, via `pypdf`) → critic scores it (`src/critic.py` `score_resume`), all packaged by the nested `evaluate(tailored)` helper (shared with the polish loop below). An attempt is ACCEPTED when it fits `max_pages` AND fills at least `min_pages` (a 1-page result for a long career history means real content was dropped — that's a failure, fed back as "restore it") AND scores ≥ `min_score` with ZERO fidelity issues AND ZERO AI-style issues. Otherwise the critic's concrete truthful fixes + any length feedback are fed into the next `tailor_resume(..., revision_feedback=...)`, up to `max_attempts`. Always keeps the BEST attempt so it terminates even if nothing is accepted. Best-ranking puts truthfulness first: `(accepted, fewer fidelity issues, fewer style issues, length in range, higher score, fewer pages)`. CLI flags: `--max-pages`, `--min-pages`, `--max-attempts`, `--min-score`.
  - **Surgical polish stage (`max_polish`, default 2; `--max-polish`, `tailoring.polish_resume`):** the re-tailor loop rewrites the WHOLE résumé each attempt with "tailor to this job" still its prime directive, so it keeps reintroducing posting-echo wording and often can't clear every flag — it would then ship the "best effort" WITH known fidelity/style problems. After the loop, if `best` still has fidelity/style flags AND its length is in range (polish can't fix length), the pipeline runs an EDITOR pass that makes the SMALLEST possible edits to remove exactly the flagged items (rename "Vendor Governance"→"Vendor Management", reword one echoed phrase) using only real base-résumé content, then re-`evaluate`s. Local edits converge where a full rewrite thrashes. Runs up to `max_polish` rounds; a polish that backfires (worse `key`) is discarded, so it can never lower quality. `meta["polish_rounds"]` records how many ran. This is the CORRECTION step — detection (critic) alone left flags in the final résumé.
  - `src/critic.py` — the automated fidelity-and-quality auditor (Claude). Catches fabrication, inflation, hedge-phrases, and posting-mirroring (`fidelity_issues`); truthful-but-AI-sounding wording — résumé-bot clichés, posting-echo phrasing, uniformly polished bullets (`style_issues`; both lists block acceptance); and real base-résumé content the draft DROPPED (surfaced via `revisions`). It must NEVER suggest adding experience not in the base resume. Each fidelity/style/revision/strength item is ONE concise sentence (≤~25 words — the schema + instructions enforce it): scannable in the UI tooltip AND small enough that the JSON reply doesn't truncate. Shares the Claude CLI call via `tailoring.call_claude_json`. **The critic's full report is persisted with the résumé** (the `resume_findings` child table, kinds fidelity/style/revision/strength; tracker rows carry it as the `"Critic Findings"` {kind: [findings]} dict, written via `log_application(critic_findings=…)` on generation AND on the "From JSON" re-score) and shown in a hover tooltip on the home page's Match cell. **Match score = the critic's quality score ÷ 10 with a truthfulness cap** (any fidelity issue caps it below 70) — it is NOT a job-fit measure (that's the AI Fit column).
  - **Cost:** a one-time evidence pre-pass call runs before Pass 1 (cacheable prefix shared with the tailor/critic calls); each pass-2 attempt is 2 Claude CLI calls (tailor + critic), plus 1 OpenAI call for the external review; each polish round adds up to 2 more (edit + re-critic) but only runs when flags remain after the loop (often 0 rounds). `--min-score` too high (e.g. 95) pressures the model and wastes attempts; 85 is a sensible default. Set `--max-polish 0` to disable the polish stage, `--no-evidence` to skip the pre-pass.
  - **Robustness:** `tailoring.call_llm_json` RETRIES ONCE on a truncated/invalid-JSON `ValueError` (a reply that stopped mid-object or looped is usually transient), so one bad critic/tailor response no longer fails the whole generation; a hard backend error (no key, network, API failure) is NOT retried and propagates. Combined with the leaner critic (above) and resumable checkpointing, a truncated critic reply is now absorbed three ways.

## Two-Pass Flow with External (ChatGPT) Review
`generate()` runs: **Evidence pre-pass** (`src/evidence.py` builds the grounding map of true requirement→evidence matches; see the pipeline bullet) → **Pass 1** (single tailor, writing from that map) → **external review** (`src/external_critic.py` sends the draft + JD to ChatGPT/OpenAI for truthful-improvement suggestions) → **Pass 2** (re-tailor applying those suggestions, then the internal Claude critic + length loop enforce truthfulness and ≤ max_pages, iterating up to `max_attempts`) → **polish** (surgical editor clears any residual flags). Every stage is checkpointed so a failure can resume (see the Resumable generation bullet).
- The two LLMs cross-check: **ChatGPT optimizes for fit** (and will sometimes suggest posting-mirroring / unsupported claims); **the internal Claude critic is the truthfulness gatekeeper** that catches and strips them. Validated: ChatGPT suggested "owned roadmap end-to-end" and a "CI/CD" relabel; the critic flagged both.
- Requires `CHATGPT_API_KEY` (or `OPENAI_API_KEY`) in `.env`. Model via `CHATGPT_MODEL` (default `gpt-4o`). Uses `requests` (no openai SDK dependency).
- Toggle off with `--no-external-critic` (CLI) or `use_external_critic=False`. If no key is present, it logs and falls back to internal-only checks.

**Per-stage LLM selection.** Each of the four LLM-driven steps can run on its own backend (`claude` / `chatgpt` / a local Ollama model), so e.g. someone without ChatGPT credits can run the external review on Claude/Local. The four stages: **1 generate** (Pass-1 tailor), **2 external review** (the fit critic; also accepts `off` to skip), **3 truthfulness check** (`critic.py`), **4 regenerate** (Pass-2 tailor loop). `generate()` takes `stage_llms={"generate","external","check","regenerate"}`; any missing key falls back to `llm=` (external falls back to ChatGPT when enabled). Web UI: the home page's "LLM selection" section — seven labeled dropdowns persisted in localStorage: the four resume stages (labeled "Resume stage 1 - Generate draft" … "Resume stage 4 - Regenerate w/ feedback") plus three STANDALONE pickers that are NOT stages and never enter `stage_llms`/the DB columns: "Base résumé - Import & Prefill" (default claude; carried to `/base-resume/import` as a hidden `import_llm` field), "Chat - Résumé enhancement" (sent in the `/chat` JSON body), and "Job scan - AI Fit verdict" (default chatgpt; rides the scan and Score-fits POSTs as `llm_fit` → `find_matches(fit_llm=…)` / `run_stored_verdicts(llm=…)`; a chatgpt fit LLM still needs the OpenAI key, claude/local don't); CLI: `--gen-llm` / `--external-llm` / `--check-llm` / `--regen-llm`. Backends live in `src/tailoring.py` (`call_llm_json` / `call_llm_text` dispatch claude/chatgpt/local; a local selection is the raw tag form `"local:<tag>"`, discovered live from the Ollama server's `/api/tags` — `list_local_models()` in `tailoring.py`, exposed via the `GET /local-models` route (in-process cached, `?refresh=1` bypasses it) that backs the web UI's "↻ Refresh local models" button; there is no fixed model list to configure — pull whatever's on the Ollama box and it shows up. **Embedding models are refused as résumé-stage backends (two-layer guard, `tailoring.is_embedding_model`):** an embedding model (nomic-embed-text, mxbai-embed, any bert-family or `*embed*` tag) only makes vectors, so picked for a generate/check/regenerate/external stage it silently produces nothing and the run shipped an UNAUDITED, fabrication-riddled résumé with a 0.0 score (a real incident). `list_local_models()` now filters them out of ALL seven chat pickers (using `/api/tags` `details.family` + the name), and `pipeline.generate()` hard-refuses any embedding model on an active stage FAST — before any LLM/render/DB cost — with a clear "pick a chat model" ValueError (catches stale localStorage/`<stage>_llm` selections the UI can't). Separately, when the critic genuinely returns no usable verdict the run still ships the draft but `meta["unaudited"]` is set and the app banner calls it UNVERIFIED (not a misleading "score 0/100"). `LEGACY_LOCAL_ALIASES` keeps the three pre-discovery nicknames (`local_qwen`/`local_gptoss`/`local_mistral`) resolving read-only for already-saved selections (old localStorage picks, old DB `<stage>_llm` rows); new selections are always `local:<tag>`. The per-model `LOCAL_LLM_MODEL_QWEN`/`_GPTOSS`/`_MISTRAL` env vars are retired — only `LOCAL_LLM_URL` (the server root) remains); ChatGPT reuses the same `CHATGPT_API_KEY`/`CHATGPT_MODEL` as the external critic. The full per-stage breakdown is persisted as four real columns on the `resumes` table (`generate_llm`/`external_llm`/`check_llm`/`regenerate_llm`); rows carry it as the `"Stage LLMs"` dict ({stage: backend}). The Stats page shows the model behind each stage; the "final" LLM (drives the "Made by" summary counts) is the regenerate-stage backend — there is no separate LLM column.
- Hard roles (very distinctive posting language) may still not reach "accepted" even after the retry + polish stages and land as "best effort" — the critic's exact findings make a quick surgical `--render-only` cleanup easy.
- `src/resume_parser.py` / `job_parser.py` / `evidence.py` / `tailoring.py` / `renderer.py` / `tracker.py` — pipeline stages.
- `src/db.py` — PostgreSQL layer: ALL SQL lives here (tracker/run_log hold domain logic only, no SQL). Connection via `DATABASE_URL` (resolved lazily at call time, so `.env` loading order can't bite); schema as **append-only ordered migrations** tracked in a `schema_migrations` table (add a new `(version, sql)` step to `MIGRATIONS`, never edit an applied one); one-time legacy-CSV import on an empty DB. **Fully normalized schema with real types:** `jobs` (the posting: company/role/location/url, `date_found`/`date_posted` DATE, `technical` BOOLEAN; board identity as real columns `source`/`board_token`/`external_id` — the packed `job_id` stays the natural PK with a CHECK enforcing the composition + a UNIQUE on the identity) ⟵FK— `job_flags` (one row per matcher warning) ⟵FK— `resumes` (1:1, the generated résumé: paths, `match_score` NUMERIC, `gen_seconds` INTEGER, one `<stage>_llm` column per pipeline stage) and ⟵FK— `applications` (1:1, existence = applied; `applied_via`, `applied_date` DATE), all ON DELETE CASCADE; `generation_log` (typed audit, deliberately no FK so it outlives deleted jobs); `job_embeddings` (1:1 child of jobs, `vector(1536)` description embedding — a child table so ~6 KB vectors stay out of `job_overview`/page loads), `job_descriptions` (1:1 child, the full posting text saved at scan time — v5; same keep-it-out-of-page-loads pattern) `resume_versions` (v12 — one row per archived résumé snapshot, PK `(user_id, job_id, version)`, FK → `resumes` ON DELETE CASCADE; archived file paths + `match_score` + `findings`/`stage_llms` as packed JSON text + `note`; written by `_snapshot_current_resume` before every regenerate, read by the 🕑 History modal — see the app.py bullet) `profile_embeddings` (cached base-résumé/target-roles vectors, keyed by content hash) and `board_directory` (v11 — the per-source list of live job boards discovery found: `source`/`token`/`job_count`/`first_seen`/`last_seen`, PK `(source, token)`; SHARED across users like the embeddings, so NO user_id; the scan reads it to know which boards to walk, discovery `replace`s it. Moved here off the old flat `data/<source>_boards.json` files — v11 imported them once and leaves them as a frozen bootstrap seed for fresh DBs, the same courtesy as the legacy CSVs); `ai_fit_score`/`ai_fit_reason`/`ai_fit_at` live on `jobs` (v4 recreates `job_overview` — a view freezes `j.*` at CREATE time, so new jobs columns need a DROP+CREATE); `job_overview` VIEW joins them for reads (flags aggregated to an array). Vectors cross the driver as text (`'[0.1,…]'::vector` casts, `embedding::text` + json on the way out) — no pgvector Python package; similarity math stays in SQL (`<=>`). No vector index on purpose (thousands of rows seq-scan in ms; revisit ≥100k). `tracker.py`/`run_log.py` keep their function signatures, and rows still flow as flat dicts keyed "Job ID"/"Company"/…, but the VALUES are typed: dates are `datetime.date`, Match Score float, Gen Seconds int, Technical bool, Flags a list, "Stage LLMs" a {stage: backend} dict, None = not set (joined text fields like HTML/PDF/Applied come back "" when absent). Templates render these directly — `app.jinja_env.finalize` maps None→"" so NULLs never print as "None" (Status stays derived: application row → Applied, resume row → Generated, else Found). A DB created by the pre-normalization flat schema is detected and refused with a pointer to the one-time `scripts/migrate_to_normalized_schema.py` (already run on the live DB; it kept `*_flat_legacy` backup tables). `data/Connections.csv` intentionally stays a file — it's a LinkedIn export you drop in, not app-owned data.

Now the tab, company search, column sort and page number are all query parameters (`?tab=&q=&sort=&dir=&page=`), the filtering/ordering/slicing happens in SQL, and only `JOBS_PER_PAGE` (250) rows are ever rendered. Badge counts + the summary tiles come from `db.count_overview_tabs`/`count_overview_summary`, counted over exactly the rows each tab renders. A stale `?tab=`/`?sort=` value falls back rather than 500-ing, and a page number past the end clamps to the last page.

It now also hides aged-out rows from the table — EXCEPT jobs you applied to (history), jobs with a generated résumé (real LLM spend), and jobs with no `date_posted` at all (unknown age, not old — the same carve-out the scan filter makes). The cutoff date is computed in PYTHON (`tracker._age_cutoff`), never as SQL `CURRENT_DATE`: `date_posted` is written with the app's local date while the docker Postgres runs UTC, so an in-database "today" is a day ahead on US evenings. The modal now POSTs to `/underqualified-threshold` and the page re-renders.

Best-effort: a failed archive never blocks the regenerate. The home page's per-résumé **🕑 History** button opens a modal (`GET /resume-versions` → newest-first list) with Preview/Download/**Restore** per version. **Restore** (`POST /restore-resume-version`) snapshots the CURRENT résumé first (so restore is itself undoable), then re-renders the chosen version from its saved JSON over the live files and points the résumé row back at that version's score/findings/LLMs (no re-score). Both buttons snapshot (user chose "both"); history is kept forever (no pruning). Version files live under `GENERATED_DIR`, so the existing `/files` route serves them and the path-traversal guard covers them.
  - **Async watchdog:** background generations are tracked in `_gen_tasks` and polled via `/generate-status`. A wedged run (e.g. the local LLM host sleeps mid-request) could leave a task at `done:false` forever and spin the UI. `GEN_TASK_TIMEOUT_SEC` (default 6 hours, env-overridable) makes `/generate-status` abandon an over-limit task with a definitive error; the client poller caps slightly higher (~6h10m) so the server message wins. The default is generous because a single local-LLM call is capped by `LOCAL_LLM_TIMEOUT` (default 1 hour, in `src/tailoring.py`) and a full all-local generation makes several such calls — slow but free. The zombie thread, if it ever finishes, finds no task slot and no-ops. **Background-generation exceptions are logged with a full traceback (`app.logger.exception` in `_start_generation`'s runner)** — previously a blow-up went ONLY into the one-shot browser result (dropped after one poll), leaving no diagnosable trace anywhere. On failure the pipeline's checkpoints survive, so `_generate_for_job_core` passes `allow_resume=True` on every generate: re-clicking the same regenerate CONTINUES the interrupted run rather than restarting it (see the pipeline's Resumable generation bullet), and the failure message tells the user so.

## Phase 2 Job Discovery — Wide Net + AI Ranking
The scan (`Retrieve Jobs` → `src/job_search.py find_matches`) deliberately over-collects and lets AI sort the catch. It runs as **ONE interleaved pass, board by board, `workers` (6) boards CONCURRENTLY** (threads; the work is ~all network waiting): each board's jobs go through the whole pipeline below (sieve → meaning net → deep screen → store+embed+score) as soon as that board is listed — so real, scored matches appear in the DB and the UI's live feed within the first minutes, NOT after all 3,000+ boards are listed. Cross-board same-company+title duplicates are skipped first-seen-wins (`processed` set); per-office duplicates collapse per board (the user's commute zone preferred). **Speed levers** (the deep screen drops ~95% of candidates, each costing a description fetch): confidently non-US candidates are dropped from LIST data before any fetch, and every deep-screen rejection is remembered in `rejected_jobs` (v6, URL-keyed — rejected postings are skipped by all future scans up front; permanent on purpose, since anything old enough to have changed gets age-dropped anyway). **Manually deleting a job (🗑) also records it there** ("deleted manually" — `tracker.delete_job`), so a deleted job never reappears in a later scan; the auto-remove on a closed posting records "posting no longer active". Description fetches and AI verdicts each retry once (transient blips were the main source of unscored rows). The pipeline per job:
1. **Title sieve** (`matching.title_qualifies`): a title qualifies with ANY ONE `domain_keywords` term / `qualifying_phrases` phrase / priority / high-value term. `generic_keywords` (manager, director, software, ai…) NEVER qualify alone — "Engineering Manager" passes as a phrase, "Account Manager" doesn't. Negative terms have a carve-out table (`matching._NEGATIVE_CARVEOUTS`): architect→learning context, sales→enablement/engineering/training, so "Sales Enablement Manager" and "Learning Solutions Architect" survive. All lists editable in Settings (`src/filter_config.py`); `min_keywords`/`title_keywords` are retired.
2. **Meaning net** (`job_search._meaning_net`): titles whose ONLY reject was the sieve (`matching.keyword_only_rejects`, reason == `matching.TITLE_SIEVE_REJECT`) are embedded (one small batched call PER BOARD; the target vector is computed once per scan) and any within `title_similarity_percent` (default 45%) of the embedded `target_roles_text` paragraph re-enter via `match_job(job, semantic_pass=True)` — which suppresses ONLY the sieve reject. Each admission is logged with its similarity % for threshold tuning.
3. **Hard drops at the deep screen** (locked user rules, `matching.match_job`): not confidently US; NO stated salary; stated salary < the user's `salary_floor`; **on-site always drops; hybrid drops unless the location matches `commutable_locations`** (the user's configured commute zone — `classify_workplace` is the 3-way remote/hybrid/onsite classifier, commutable hybrids pass with a flag); contract/part-time/gig; stale postings.
4. **Store + embed + AI-score, per job** (`job_search._store_and_score`): the moment a job passes the deep screen it is embedded (one small OpenAI call), upserted into `jobs` **with its full posting text** (`job_descriptions` table — so nothing ever re-fetches from a board again), and immediately AI-scored by ChatGPT (1-10 + one-line reason → `ai_fit_*` on `jobs`, the **AI Fit** column; tooltip = reason). One job at a time: the home page fills up WHILE the scan runs, and an interrupted scan keeps everything processed. Each step degrades gracefully (no OpenAI key → stored without Match %/AI Fit; per-job failures logged, never fatal). The returned job dicts carry `stored` ('added'|'refreshed') and `ai_fit_score`; `_prepare_fit_scoring` does the once-per-scan setup (résumé text + already-scored ids — re-discovered jobs keep their verdict). **AI Fit is the ONLY score column shown** (reason in a styled hover tooltip on the cell — CSS `data-tip`, not a native title). The old Job Fit stars column is gone and Match % is hidden from the UI, but the similarity machinery stays: `db.fetch_similarity_map` (`<=>` vs the base résumé's cached vector) still drives the home-page sort (AI Fit first, similarity as tiebreak), the meaning net, and backfill ordering.
5. **Backfill** (`fit_verdict.run_stored_verdicts`, the "Score fits (AI)" button / `POST /fit-verdicts`): scores EVERY stored-but-unscored job — embedded ones from their STORED description (board re-fetch with one polite retry only for pre-v5 rows), plus rows with no embedding at all (pre-vector rows: recover text → store it → embed → score, so they finally get Match % + AI Fit too). Skips only jobs whose text is truly unrecoverable (pasted-text manual rows, dead postings) — each skip/failure is printed to the app log. Once the backlog is scored it's redundant with the scan's per-job scoring and is slated for removal. The old `fit_verdict_top_n` setting is retired (`run_stored_verdicts(top_n=...)` still accepts a cap programmatically).
- `src/embeddings.py` — the OpenAI embeddings client (`text-embedding-3-small`, `requests`-based like the chat calls, batched, no SDK). **Two backends, switched globally (not per-user — job embeddings are shared) via `.env`:** `EMBEDDING_BACKEND=openai` (default, `text-embedding-3-small`) or `local` (Ollama `{LOCAL_LLM_URL}/api/embed`, model `LOCAL_EMBEDDING_MODEL`, default `nomic-embed-text`, stored model string `ollama:<tag>`; needs no OpenAI key — `available()` is True). Vector columns are dimensionless since migration v10; every vector row carries a `model` tag and ALL similarity SQL filters on `embeddings.active_model()` (mixed-dimension `<=>` is a SQL error, so stale-model rows are invisible, not deprioritized). **Switch procedure:** `ollama pull <model>` → set `EMBEDDING_BACKEND=local` → restart → press "Score fits (AI)" once — the backfill re-embeds missing AND retired-model rows from stored descriptions; existing AI Fit verdicts survive (they judge text, not vectors). Profile vectors (base résumé + target-roles paragraph) are cached in `profile_embeddings` keyed by content hash — **replacing the base résumé auto-clears all AI fit verdicts** (they were judged against the old résumé) and re-embeds at the next scan. `cached_base_resume_embedding()` is the read-only page-load path (never calls OpenAI).
- **Cost:** embeddings ≈ $0.02 per 1,000 descriptions (negligible); verdicts = one gpt-4o call per NEW job ≈ $0.25-0.40 per 25 jobs (a 500-job first scan runs a few dollars; routine scans only score what's new). **No OpenAI key → graceful degrade:** keyword sieve still works; meaning net, Match %, and AI Fit are skipped with clear log lines — OR go fully key-free: `EMBEDDING_BACKEND=local` plus a claude/local "Job scan - AI Fit verdict" picker keeps all semantic features running with zero paid-API calls.
- Old rows (pre-feature) have no embedding → they sort to the bottom until "Score fits" backfills them (it embeds them too).
- The scan's live UI: one progress stage ("scan" — done/total = BOARDS, ★ found = STORED matches, not title candidates); `/retrieve-status` carries a `recent` feed (the last ~10 stored jobs + scores); the scan card renders it so finds appear immediately, and the page auto-reloads when the scan finishes (message survives via sessionStorage; skipped if a modal is open).
- **Drop-funnel audit** (`src/scan_audit.py` `ScanAudit`): every scan writes a full per-job, per-stage-event trail straight to Postgres (`scans` + `scan_events`, v13) — no `.log` file. One `scans` parent row per `find_matches()` call, plus one `scan_events` row per job per stage transition (sieve_pass/list_screen/pre_fetch_us/dedup/fetch/deep_screen/store); events are buffered in memory and flushed in batches so the 6 board threads aren't each paying a DB round-trip per line, and summary tallies (sieve/meaning-net counts, drop-reason buckets, stored count) are derived on read rather than stored. Browsable at the gated `/developer/scan-audits` viewer (behind the `DEVELOPER_OPTIONS` env flag): a scan list with derived tallies, drilling into one scan's paginated event table with stage/outcome/reason-bucket/company filters. A DB write failure is logged and swallowed — it never breaks the scan. **Manual rescue (v14):** the events viewer has a gated `POST /developer/scan-audits/add-job` ("➕ Track this job") button on eligible *dropped* cards — it re-fetches the posting from its board connector, stores it into the user's tracked jobs (same embed→store→AI-score path as the scan), clears its URL-keyed rejection, and appends a distinct `manual_add` event (labeled with the job's audited company/title so it groups with the drop, shown as an "added by me" badge). This is why `scan_events` gained `external_id`/`url` (v14): the identity needed to re-fetch a dropped job later. Every card with a saved `url` also shows a "View posting ↗" link (new tab) so you can open the live posting to judge or debug it before tracking.
- `date_found` gotcha: it's written with the APP's `date.today()`, not the DB's `CURRENT_DATE` — the docker Postgres runs UTC, which is already "tomorrow" on US evenings.

## Tech Stack
- Language: **Python**
- Output format: **HTML + PDF** (HTML for easy reading/editing in IntelliJ; PDF for ATS submission)
- Database: **PostgreSQL 16 + pgvector in Docker** (image `pgvector/pgvector:pg16` — plain PG16 plus the `vector` extension, needed for job-description embeddings; migration v4 raises a fix-it error against a plain postgres image; `docker compose up -d db`; the data directory is the gitignored `./postgres_data` bind mount — plain files on the host, immune to Docker volume/desktop deletion). App connects via `DATABASE_URL` (default `postgresql://resume:resume@localhost:5432/resume_handler`; compose overrides the host to `db` inside the app container). First run against an empty DB auto-imports the legacy CSVs and leaves them on disk as backup.
- Deployment: **Docker Compose** (`Dockerfile` = python:3.12-slim + Playwright Chromium + Node/`claude` CLI). Deps install from `requirements.lock` (pinned resolve — regenerate per the header in `requirements.txt` after changing direct deps). The app runs as non-root (`appuser`; Chromium therefore launches `--no-sandbox`, set in `renderer.py`). `/health` round-trips the DB and backs the compose healthcheck; `init: true` reaps CLI/browser subprocesses. `resumes/`, `data/`, `logs/` are volume-mounted; `.env`/personal data are `.dockerignore`d out of the image.
- LLM: the **"claude" backend has TWO paths, chosen automatically** (`src/tailoring.py`):
  - **Metered Claude API (preferred).** When `CLAUDE_CODE_API_KEY` is set in `.env`, the "claude" backend calls the Anthropic Messages API via the official `anthropic` SDK (`_call_claude_api_text`/`_json`, model `claude-opus-4-8`, override via `CLAUDE_API_MODEL`; `CLAUDE_API_MAX_TOKENS` default 8192). This is pay-as-you-go — cheaper per call and, crucially, **NOT session-capped** like the subscription CLI. It's a plain non-streaming, non-thinking call that returns raw JSON (same `_extract_json` path as every other backend). **The key is passed EXPLICITLY** (`Anthropic(api_key=CLAUDE_CODE_API_KEY)`, never a bare `Anthropic()`) because the SDK doesn't auto-discover a key stored under this non-default env var. `CLAUDE_CODE_API_KEY` is a distinct var from `CLAUDE_CODE_OAUTH_TOKEN` (the container CLI auth).
  - **`claude` CLI subscription (fallback).** With no `CLAUDE_CODE_API_KEY`, the "claude" backend falls back to the `claude` CLI in print mode (`claude -p`, prompt piped via stdin), which uses the user's Claude.ai Pro subscription (session-limited).
    - In the **app container**, the CLI can't use the Mac's keychain login — auth comes from `CLAUDE_CODE_OAUTH_TOKEN` in `.env` (generate once on the host with `claude setup-token`; it passes through to the subprocess env, which now inherits the parent environment unfiltered).
  - Both paths are interchangeable behind `call_llm_json`/`call_llm_text`, so the two-pass pipeline, critic, polish, chat, and per-stage LLM selection all use whichever is active with no other changes. The `anthropic` SDK is a real dependency again (in `requirements.txt`/`.lock`).

## PDF Layout Gotcha (read before tweaking page length)
The PDF's effective page margin is controlled by the **Playwright `margin` setting in `src/renderer.py`** (currently 0.45in top/bottom), NOT by the `body { padding }` in `templates/resume.html` — the print media query (`@media print { body { padding: 0 } }`) zeroes that padding for the PDF. So editing body padding does nothing to the PDF. To reclaim/add vertical space on the PDF, change the Playwright margin in `renderer.py`. (The body padding only affects HTML preview in a browser/IntelliJ.) To fit ~2 pages, prefer adjusting the Playwright margin and section spacing over shrinking the font.
